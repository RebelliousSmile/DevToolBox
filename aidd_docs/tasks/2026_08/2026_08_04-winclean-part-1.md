# Instruction: winclean Part 1 - core + guards + safe removal + `safe` dev modules

### Import mechanism (must be settled in Phase 1, before any other code)

**Copy the mechanism `scripts/system_inventory/inventory.py` already uses; do not invent one.** That file states the problem in its own docstring and solves it in four lines: compute the repo root as `Path(__file__).resolve().parent.parent.parent`, insert it into `sys.path` if absent, then import **fully qualified** — `from scripts.system_inventory.common import ...`. winclean does the same, with the same spelling, and `clean.py`'s own intra-package imports follow it (`from scripts.winclean.guards import ...`).

Two invocations must both work and they fail for opposite reasons, which is why the repo-root insert is not optional: `python scripts/winclean/clean.py` sets `sys.path[0]` to `scripts/winclean/` and the repo root is nowhere on the path, while `python -m unittest discover -s scripts/winclean/tests` run from the repo root already has it as `cwd`. The insert makes one import spelling valid in both.

The spelling is **`scripts.system_inventory.common`**, never a bare `system_inventory.common`: inserting the repo root puts `scripts/` on the path as a parent directory, not as a path entry, so only the qualified form resolves. An earlier draft of this paragraph prescribed the repo-root insert *and* the bare import — a pair that cannot both be right, and the bare one is the half that would have failed at the first run. `scripts/` needs no `__init__.py` for this: Python resolves it as an implicit namespace package, which is exactly how `system_inventory` imports itself today, and adding one would change how `deps_audit` and `system_inventory` are discovered. `scripts/winclean/__init__.py` **is** created, as `scripts/system_inventory/__init__.py` exists. Do not copy `common.py`.

### Files to create

- `scripts/winclean/__init__.py` - package marker.
- `scripts/winclean/common.py` - `Level` (`safe`/`moderate`/`aggressive`), `CleanCandidate` (`module`, `path: str | None`, `label: str`, `estimated_bytes: int | None`, `level`, `reason`, `no_undo: bool`, `needs_network: bool`, `stat_mtime: float | None`), `CleanResult` (`module`, `estimated: int | None`, `freed: int | None`, `recycled`, `failed`), `CleanModule` (`name`, `level`, `requires`, `discover`, `clean`, `discovery: "walking" | "fixed" | "pathless"`, `proc_guard: "warn-and-skip" | "warn-only" | None`, `needs_network: bool`), plan/report formatting, `to_json_payload()`. Reuses `scripts.system_inventory.common`'s `human_size` and `dir_size_on_disk` rather than reimplementing them (the qualified spelling is the only one that resolves - see **Import mechanism**).
  The last three `CleanModule` fields are **the declared per-module properties, with no default**, and they are exactly the three the mapping tests of **Phase 3** read: `discovery` (master decision 15 — declared in Phase 3 task 5, consumed by Phase 4 task 3), `proc_guard` (decision 19 guard strength, `None` meaning "this module runs no process check"), `needs_network` (decision 11). A default would let a new module inherit a classification silently, which is precisely what those tests exist to prevent. `needs_network` is declared **here**, on the module, and the plan builder stamps it onto every candidate `discover()` returned (Phase 4 task 3) — the stamping is in the caller, not in each `discover_*()` body, so there is one writer of the field and a module cannot contradict its own declaration. The mapping test then reads the registry rather than instantiating each module, which is what "over the currently registered set" requires. The identically named `CleanCandidate` field keeps its `False` default — that default is a construction convenience for tests and carries no classification, whereas the module-level one is a decision.

Deriving it from one list makes uniqueness structural — a tuple index cannot collide — where three documents each hand-numbering their own modules would manufacture exactly the collision the uniqueness test detects. ## Risk register

| Risk | Impact | Mitigation |
| ---- | ------ | ---------- |
| A guard is bypassed because a module builds its own paths | Deletion outside scope | Modules **never** delete: they only return candidates. `clean.py` is the sole caller of `remove.py`, and it always routes through `guards.py` first. Enforced by test: no `mod_*.py` imports `remove` |
| `normcase` forgotten on one comparison branch | Mixed-case protected path silently unprotected | `is_protected` takes only pre-`normalise`d inputs and asserts it; test feeds `C:\Users\X\.cargo` vs `c:\users\x\.CARGO` |
| `\\?\` prefix applied to a relative **or unresolved** path | Prefix silently invalid, or - because the prefix disables normalisation - a literal `..` component sends the deletion at a path no guard evaluated | `long_path()` raises on a non-absolute input **and on an absolute one still carrying `..`/`.` or a trailing dot or space** (Phase 2 task 1); unit-tested in both directions |
| `SHFileOperationW` struct layout wrong under `ctypes` | Undefined shell behaviour on a delete call | Struct field-for-field against the Win32 signature; the flag set, the two failure conditions and the meaning of the return value are stated once in Phase 2 task 4 and not repeated here - this row previously listed three flags where the task lists four, and the missing one was `FOF_NOERRORUI`, whose absence lets the shell raise a modal error dialog inside a process the launcher spawned with `CREATE_NO_WINDOW`: an invisible dialog is an indefinite hang. Exercised on a temp file in a guarded live test |
| `cargo-target` discovery matches a `target/` that is not a build dir | Deleting user data named `target` | A `target/` is a candidate only if a sibling `Cargo.toml` exists **and** it contains a `CACHEDIR.TAG` or a `debug`/`release` subdir; unit-tested against a decoy |
| Walking the whole disk for `Cargo.toml` is unbounded | Run appears hung | Discovery roots are explicit (`--root`, repeatable; default: **the repo root only**, master decision 15), capped at `--max-depth` **6**, reparse points skipped, and bounded by a ≤ 60 s acceptance criterion on that default root |
| A `--root` points into a cloud-synced tree | Every deletion propagates to the cloud provider and consumes remote versioning quota | `%USERPROFILE%\Documents` is deliberately **not** a default root (master decision 15 — it is a MEGA-synced vault on this machine). A resolved root under a known sync root (`Documents\Perso`, OneDrive, Dropbox, iCloud) prints a **sync warning** in the plan header; the warning is informational and never blocks |
| `--apply` reachable from config | Silent destruction | `--apply` parsed only by `argparse`; Part 3's config loader has no key for it (asserted by test there) |
| Two modules claim the same path (`__pycache__` under a `target/`) | Double-counted estimate, then a "vanished path" failure on the second module | `guards.absorb_nested()` runs after guard filtering and before the ceiling; the **ancestor** keeps the candidate and its descendants are reported as absorbed (master decision 13 — depth alone decides nesting). The ownership rank — a module's index in `registry_mod.py`'s `MODULE_ORDER` tuple — only breaks a tie between two candidates on the **exact same** path; it is unique by construction and the tuple's coverage of the registry is tested |
| A build writes into `target/` between plan and `--apply` | Corrupted build tree | Primary guard: `procs.is_running({"cargo.exe", "rustc.exe"})` warns at plan time and skips the candidate under `--apply` without `--yes`. The apply-time re-`stat` is a **secondary** guard and its limit is known (master decision 19: a directory's `st_mtime` tracks only its direct entries, so a write into `target\debug\deps\` leaves `target\`'s mtime untouched) — the residual risk is written in the README, not papered over |
| A `needs_network` purge strands an offline machine | No build possible until connectivity returns | `needs_network` is declared on the module and stamped onto its candidates, shown in the plan, and `--offline` excludes those candidates wholesale; documented in the README |
| `--only` used to reach a higher level's module | Confirmation gate bypassed from the command line | `validate_level()` rejects it non-zero before discovery, naming the required `--level` (master decision 12); tested |
| Interrupted `--apply` leaves no trace of what was destroyed | Unauditable partial deletion | The report is emitted from a `finally` block (master decision 17); Part 3 writes the history line from the same block with `status: "interrupted"` |
| A plan is printed where nobody reads it | User believes nothing was found | The terminal is the official invocation path (launcher actions carry `CREATE_NO_WINDOW`); `--out <path>` persists the report to a file. Stated in the README, not left implicit |

## Implementation phases

### Phase 1: Model + guards (`common.py`, `guards.py`)

> Pure logic, fully unit-tested, no filesystem mutation anywhere in this phase.

#### Tasks

1. Create `scripts/winclean/__init__.py` and `tests/__init__.py`.
2. Define `Level`, `CleanCandidate`, `CleanResult`, `CleanModule` in `common.py`. `estimated_bytes: int | None` — `None` means *unmeasurable*, never coerced to `0`. **`None` is the only encoding of unmeasurable anywhere in the package**: there is no companion `unmeasurable: bool` on `CleanResult`, because a flag beside a nullable number is two encodings of one fact and they drift — a result could claim `unmeasurable=False` while carrying `freed=None`, and Part 3's report already renders `null` as `—`, reading the number rather than the flag. So `freed` is `int | None` too, and any code asking "was this measured?" tests the value. This is the same reasoning that made `ownership_rank` derived rather than declared: one representation, no reconciliation.

    **`CleanResult` also carries the skipped candidates, and this task is the authority on where a skip status lives.** The field is a list of entries holding the candidate's `label`, its `path` (`None` for a pathless one), the status token and the `reason` string - not a byte column. Five tokens are emitted by the apply path of Phase 4 task 4 (`skipped-running`, `skipped-gone`, `skipped-changed`, plus `skipped-unconfirmed` and `no-undo` from the later parts) and until now the model had nowhere to put any of them, while two other documents already depended on their being there: a criterion below asserts a candidate "is reported `skipped-changed`", and Part 3's history task states that skipped candidates "surface in the printed report". With no field, the implementation is a local list inside the apply loop, and then `format_result_report` cannot read them, its three-column specification is met without a skip ever being printed, and the criterion passes on any `print()` - including one absent from `--json` and from the `--out` file, so a programmatic consumer sees a plan promising bytes and a result short of them with nothing explaining the difference. That difference is the *only* thing the estimated-versus-freed report cannot otherwise account for, which is precisely why the tokens were named.

    **It is deliberately not a byte total.** A `skipped_bytes` column would be summed into a reconciliation by the first reader who saw it, and skipped bytes were never freed, never recycled and never failed; the estimate they belong to is already in the plan. **And it does not contradict Part 3**: that part's rule that no `skipped-*` status carries a field of its own concerns the **history record**, where the deliberate split is "the record answers what was removed, the report answers what was not and why". This field is on the report side of that split - it feeds `format_result_report` and `to_json_payload`, not `history.jsonl`.
2b. **Pathless candidates must exist in the model from the start.** `path: str | None`: `None` marks a candidate that reclaims through an **external command** rather than a filesystem path — in v1 only Part 2's `docker-light` (`docker system prune -f`). Without this, the guard chain rejects it outright (`path_sanity` refuses anything under 10 characters) and Part 2 would have to bypass the guards, which is exactly what must not happen. The rules: `label` is mandatory and carries the display name — and "mandatory" here means a `__post_init__` that raises `ValueError` on an empty or whitespace-only `label`, not merely a field without a default, because a dataclass accepts `label=""` and a pathless candidate with no label is a plan row naming nothing and an unremovable audit entry; `is_protected`, `path_sanity` and `absorb_nested` **skip** pathless candidates — there is no path to protect and no nesting to resolve; the byte ceiling still counts their estimate when it is not `None`; `remove.py` is never invoked for them, the module's own `clean()` runs the command, which is why `CleanModule` carries a `clean` callable at all; they are never recycled, so they are never `no_undo`.
3. Import `human_size` and `dir_size_on_disk` **from `scripts.system_inventory.common`** using the mechanism settled in **Import mechanism** above; do not copy the code. The spelling is part of the instruction, not a shorthand for it: the bare `system_inventory.common` does not resolve under either invocation.

3b. **Know what the reused estimator does and does not report, because task 2's nullability rule does not survive a naive reading of it.** `dir_size_on_disk` returns an `int`, always: it swallows every `OSError`/`PermissionError` per entry and continues, so an unreadable subtree contributes nothing and the function **cannot** return `None`. Left alone, that turns "unmeasurable is `null`, never `0`" into an invariant no path-typed candidate can ever exercise, and — worse — reports a profile whose ACLs deny listing as a candidate of `0` bytes, which reads as *empty* rather than as *unknown*. That is the exact confusion the rule exists to prevent, arriving through the one function the rule never examined. So:
    - The estimator is not reimplemented and not wrapped per entry. Instead, each path-typed candidate attempts a single `os.scandir()` on its **own root** before pricing: if that raises, `estimated_bytes` is `None` and the plan shows `unknown`. One syscall per candidate, and it makes `None` reachable for the failure a user can actually act on.
    - Below that root the estimate stays **best-effort and may be silently low** — a denied subtree inside a readable candidate is invisible to the walk. The plan does not pretend otherwise, and neither does the ceiling: `--max-delete-bytes` is checked against a possibly under-reported total, so it is a guard against an *order-of-magnitude* path bug, not an exact budget. Part 3's `measured` column is the authority after the fact, which is why it exists.
    - `dir_size_on_disk` sums `st_size` — the **logical** size, despite the function's name — so NTFS-compressed or sparse files over-report. This is consistent with frozen decision 8 excluding `.vhdx` outright rather than trying to price it, and it is the second reason an estimate is never presented as a promise.
    - One property of the reused walk is worth relying on rather than re-deriving: it skips entries carrying `FILE_ATTRIBUTE_REPARSE_POINT` and never follows them, which matches the deletion rule of Phase 2 task 3. Estimate and removal therefore agree on the tree's boundary — had they disagreed, every junctioned candidate would have shown an estimate for bytes the removal would refuse to touch.
4. Implement `format_plan(candidates)` (descending estimated bytes, `None` last, **plus a dropped, an absorbed and an excluded section**), `format_result_report(results)` with distinct `freed` / `recycled` / `failed` columns **and a skipped section listing each skipped candidate with its status and reason**, and `to_json_payload()`, which carries that section under its own key.

    **The plan's three sections are defined here, because the criteria of Phase 4 assert them and nothing else specifies them.** A candidate the guard chain removed appears in the **dropped** section with its path and a reason class - `protected` or `sanity`, the machine token, never the French sentence (master decision 20). The two classes are reported alike and **exit differently** - `protected` continues at `0`, `sanity` aborts non-zero - which task 4 of Phase 4 decides and this section only renders. A candidate `absorb_nested()` returned appears in the **absorbed** section naming the ancestor candidate that kept it, so a reader can see why bytes counted once. A candidate `--offline` removed appears in the **excluded** section with its label and its estimate, since `--offline` is a filter like the other two and its silence has the same shape: master decision 11 exists because deleting a `needs_network` cache on a disconnected machine strands it, so a plan that **withheld** such candidates must not look like a machine that has none. It is the one filter of the three the user asked for, which is an argument for making the report short, not for dropping it. All three are data, so all three have a payload key by the general rule below. **Silence here is the failure this section prevents**: the guard chain, `absorb_nested()` and `--offline` are the only three steps that remove a candidate a module actually found, and Part 3's `PROTECTED_PATHS` lets a user add protected paths from a config file - so without these sections a module that discovered plenty and reports nothing looks exactly like a module that found nothing, which is iteration 60's defect with a config file as its cause instead of a plan bug.

    **The payload also carries the warnings the run printed, and this task is their authority.** Every warning line - the plan header's and the ones raised per candidate - has an entry keyed by a stable English code, holding the fields its sentence uses; the French text is a rendering of that entry and never its source (master decision 20). Written as a rule over warnings rather than as the two codes v1 happens to have, so a part adding a warning cannot leave the payload behind. This matters where it is least visible: a launcher-spawned action can surface only the `--out` file (master decision 16) and what it prints is a **plan**, so a warning living on stdout alone never reaches the one user who has no stdout to read. **The general rule, which this task owns and which closes the question for every part: whatever the text report states as *data* has a payload entry, and whatever it states as *prose* does not.** Data means the candidates and their fields, the byte columns, the skipped list, the failure path lists Part 2 adds, the warnings above, the estimated-vs-measured pair Part 3 adds, and the per-volume free space before and after. Prose means the level table, the dry-run footer, the deferred-reclamation footer and every explanatory sentence: a caller that needs those has the data they were computed from. The rule is stated because the alternative was found the expensive way - five separate passes each carrying one more field into the payload after the text formatter already had it - and because a rule covers the field a part invents next, which no enumeration here can. Its two halves both matter: the first prevents a figure existing only on stdout, the second prevents the payload accumulating rendered sentences that a consumer would then parse. The section is what makes the gap between the plan total and the freed total explainable rather than mysterious; three byte columns and no skip list is a report that shows a shortfall and never says why. It is a list, not a fourth byte column, for the reason given in task 2.
5. Implement `guards.normalise()`, `is_protected()`, `path_sanity()`, `absorb_nested()`, `enforce_ceiling()`, and `DEFAULT_PROTECTED`. `enforce_ceiling()`'s abort message names the plan total, the limit in force **and** `--max-delete-bytes` — an aggressive plan on a genuinely full machine can legitimately exceed 50 GiB, and a ceiling that stops the run without naming the knob turns a guard into a dead end.

    **This task is the authority on what each guard does**, and the file list above only names them. `normalise()` returns the absolute, resolved, `normcase`d form and every comparison in the package goes through it. `is_protected(path, protected)` matches an exact protected path **or any path under one, after resolution**, so a junction into a protected tree is caught. `path_sanity()` refuses a path shorter than 10 characters, the profile root itself, any drive root and any UNC share root. `absorb_nested()` applies master decision 13: a descendant of another candidate is dropped and returned separately as absorbed, exact-path ties going to the lower `ownership_rank`.

    **`enforce_ceiling()` meets `estimated_bytes = None` on its first run, so this task settles it.** The total is the sum over candidates **whose estimate is known**; an unknown one contributes nothing to the arithmetic, because `sum()` over a list holding `None` raises and the alternative of coercing it to `0` is the same statement made silently. Silence is what is refused here: the ceiling's promise is that no run removes more than the limit without the user raising it, and a plan carrying an unpriced candidate cannot keep that promise — Part 2's `docker-light` can reclaim tens of gigabytes behind an estimate of `None`, so a plan totalling 2 GiB may free far more. `enforce_ceiling()` therefore **reports the total as partial and names the modules that contributed no figure**, whether or not it aborts, and that notice is a warning under Phase 1 task 4's rule (code `ceiling-total-partial`, carrying the module names) rather than a sentence only stdout sees. It does **not** abort on an unknown estimate: refusing would make one pathless module veto every plan it appears in, which no decision in this package asks for.

    **`DEFAULT_PROTECTED` holds the user-data roots that no module in any part emits a candidate under**: the shell folders for documents, desktop, pictures, videos, music and downloads, read from the environment at import and normalised, never written as literal `C:\Users\<name>\...`. That membership test is the rule, and it is a rule rather than a list because the set has one failure mode in each direction. Too narrow - the empty set - and the package's last line of defence against a path bug is the ceiling alone. Too broad and it **cancels modules silently**: `is_protected()` matches subtrees, so the profile root, `%LOCALAPPDATA%` or `%APPDATA%` would each protect the very trees `temp-files`, `browser-cache` and the package caches emit candidates inside, and every one of them would report nothing with no error - the composition iteration 60 already had to remove from Part 2. **The profile root is therefore absent from this set on purpose**: `path_sanity()` refuses it as a *candidate*, so no module can ever propose it, and protection is not the mechanism that has to say so.

    **The chain runs on candidates, not on roots**, exactly as the flow above shows: `normalise()`, then `is_protected()`, then `path_sanity()`, applied to each candidate `discover()` returned. It **returns what it removed, with the reason class, rather than filtering silently** - the plan builder of Phase 4 task 3 hands that list to the dropped section of task 4. A guard is allowed to refuse a candidate; it is not allowed to make one disappear. A `--root` is **not** put through it, and that is a decision rather than an oversight - `path_sanity()` refuses paths shorter than 10 characters, so screening roots with it would abort the run on a legitimate `--root C:\dev`, and master decision 15 already settled how a dangerous root is handled: the cloud-sync root **warns**, it does not refuse. Said here because an implementer holding a function called `path_sanity` and a list of user-supplied roots will reach the wrong conclusion unaided.

### Phase 2: Windows-safe removal (`remove.py`)

> The single place in the package allowed to destroy anything.

#### Tasks

1. `long_path(p)`: assert the path is absolute **and already resolved**, normalise separators, prefix `\\?\` (or `\\?\UNC\` for UNC). Absoluteness alone is the wrong assertion, and this is why the stronger one is written here: the `\\?\` prefix **switches off Win32 path normalisation**, so `..`, `.`, and trailing dots or spaces stop being resolved and reach the filesystem as literal component names. `Path('C:/a/../b').is_absolute()` is `True`, so a check for absoluteness admits exactly the input whose meaning the prefix changes - and it changes it silently, into a different path from the one every guard upstream evaluated, since the protected-path subtree match works on resolved paths. `long_path()` therefore raises on any input carrying a `..` or `.` component or a trailing dot or space, rather than repairing it: repairing would place a second, quieter path resolution below the guard layer instead of in front of it. **This task also owns the prefix's blast radius, and it is narrow: the prefixed form is produced at the syscall boundary inside `remove.py` and never leaves it.** It is never stored on a `CleanCandidate`, never returned to a caller, never compared against another path, never printed. `CleanCandidate.path` and every path in `CleanResult`, `locked_paths`, the report and the `--json` payload hold the plain resolved form. Three reasons, each checked rather than assumed: `SHFileOperationW` **rejects** `\\?\` outright, so `recycle()` and `can_recycle()` must receive the unprefixed path (master risk register); `dir_size_on_disk`'s `exclude_paths` match is a **lexical** `os.path.normcase(os.path.normpath(...))` comparison - verified in `scripts/system_inventory/common.py`, and documented there as deliberate - so a prefixed path silently matches nothing and the exclusion becomes a no-op; and the protected-path subtree match, `absorb_nested`'s nesting test and `--only`'s bookkeeping all compare candidate paths against each other and against `DEFAULT_PROTECTED`, which are plain. One path with two spellings is how a guard comes to evaluate a string nothing will ever delete.
2. `delete_tree(path)`: iterative walk; a reparse-point directory is removed with `os.rmdir`/`os.unlink` **without** descending; regular entries unlinked via long-path form; every `OSError` captured per entry into a `failed` accumulator with its `winerror`; returns `(deleted_bytes, failed_bytes, errors)`.
3. `can_recycle(path)`: `False` if the long-path form exceeds MAX_PATH, or the volume is not fixed. "Fixed" is decided by `kernel32.GetDriveTypeW(root)` returning `DRIVE_FIXED (3)` — never by a heuristic on the path prefix; an unknown or failing return means `False`.
4. `recycle(path)`: `SHFILEOPSTRUCTW` via `ctypes`, `FO_DELETE`, `FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_NOERRORUI | FOF_SILENT`, double-null-terminated `pFrom`; check the return code and `fAnyOperationsAborted`. This task is the single authority on that flag set: all four flags are required, and `FOF_NOERRORUI` is not decoration - without it the shell may raise a modal error dialog, which in a launcher-spawned process (`CREATE_NO_WINDOW`, decision 16) is an invisible window nobody can dismiss. **The return value is not a Win32 error code**: `SHFileOperationW` returns its own `DE_*` codes, which do not live in the system error space, so `ctypes.WinError()` and `GetLastError()` produce a plausible but unrelated message for them. The raw integer goes into the failure detail as-is. A non-zero return **or** `fAnyOperationsAborted` set means the candidate is counted `failed` with reason `recycle-failed` and left in place — there is **no** fallback to `delete_tree` (master decision 14).
5. `measure_freed(before_bytes, path)`: re-measure after the operation; return `None` (unmeasurable) rather than a guessed number when the path is gone but was never sized. A difference that comes out **negative** — the tree grew between the two measurements, which a concurrent writer makes possible — is reported as `0`, since a negative contribution would understate a real total instead of merely mismeasuring one module.

    **`freed` has one source and it is not this function.** `CleanResult.freed` is the sum of `delete_tree`'s per-entry `deleted_bytes` — the only figure that stays correct when part of a tree is locked, because it counts what was actually unlinked rather than differencing a directory that still holds the survivors. `measure_freed()` is the independent whole-candidate re-check, and it feeds **only** Part 3's `measured` column, whose entire purpose is to be compared against the estimate by a second method. Left unassigned, the two would both look like the obvious source for `freed`, and on a partially-locked tree they disagree by exactly the locked bytes — the case this level meets most often. So: `delete_tree` answers "what did we remove", `measure_freed` answers "what does the disk say now", and neither is derived from the other.

    **The other two columns had no source at all, and this task is the authority on all three.** `freed` was pinned above; `recycled` and `failed` were left to whichever number the implementer had to hand, and neither has an obvious one: `SHFileOperationW` reports **no byte figure**, and `delete_tree` is never called on a recycled candidate, so nothing in the package measures a move to the Bin. The rules:
    - **`recycled`** is a `dir_size_on_disk` measurement of the candidate root taken **immediately before** the successful `recycle()` call - not the plan-time `estimated_bytes`. Two reasons, and the second is why this is not a detail: the plan can be minutes old, and after the move the tree is no longer at that path, so this is the last moment a measurement is possible at all. Sourcing it from the estimate would also make Part 3's `measured` column identical to `estimated` for every recycled candidate, retiring the second opinion that column exists to be.
    - **`failed`** has two sources by necessity, which is stated rather than left to be discovered: for an entry that raised inside `delete_tree` it is that entry's `st_size`, already accumulated as `failed_bytes` by task 2; for a `recycle-failed` candidate (task 4, master decision 14) it is the same pre-operation measurement as above, which is still takeable because nothing was touched. **It is never `0`.** A whole candidate abandoned in place while the column reads `0` prints a report of `freed 0 / recycled 0 / failed 0`, indistinguishable from an idle run - on the one outcome decision 14 exists to make loud.
    - When a contribution is unmeasurable the existing convention applies and no new one is invented: a figure is the sum of the **known** contributions, and it is `None` only when no contribution in that `CleanResult` was measurable. A single `None` candidate must not null a total that holds exact bytes for the others - that is the same best-effort-and-possibly-low reading task 3b already fixes for the estimate, and Part 3's `measured` column is again the authority after the fact.
    - **`measure_freed`'s `before_bytes` is that same measurement, and a candidate is measured once.** The signature takes the number from its caller and nothing said where the caller finds it; the reachable answer is `candidate.estimated_bytes`, the number already in hand - and the criterion below spells out the consequence without meaning to: with a known `before_bytes` and the path gone, the function returns exactly that number. Sourced from the plan, Part 3's `measured` is therefore **equal to `estimated` for every candidate that was fully removed** - the normal outcome of every level - and its delta column is structurally `0`. The comparison that part exists to publish would be a number checked against itself. So: under `--apply` each candidate is measured **once**, immediately before it is touched, and that single figure feeds `recycled`, a `recycle-failed` candidate's `failed` and `before_bytes` alike - one measurement, three consumers, nothing to reconcile.
    - Two consequences of that sharing, stated so neither is later read as a bug: for a recycled candidate `recycled` and `measured` are **the same number by construction**, and for a directly deleted one `freed` (unlink accounting) and `measured` (whole-tree walk) may differ by the locked bytes without either being wrong. If the pre-operation walk cannot size the root - the `os.scandir` case of task 3b - the figure is `None`, so that candidate's `recycled`, `failed` and `measured` are `None` rather than `0`.
    - **A candidate that is never touched is never measured**, and therefore contributes `None` - not a number below its estimate. The measurement is taken immediately before acting, so a candidate skipped by a guard, a confirmation or a vanished path never reaches it. This is the honest value and also the more informative one: `None` says *not attempted*, while a number below the estimate says *attempted and partly prevented*, which is the locked-file case. Reporting a skip as the latter conflates the two outcomes a user most needs to tell apart.
    - The cost is one walk per candidate beyond the plan's, under `--apply` only. It is accepted rather than optimised away, because the second walk at a second moment **is** the independent check; re-using the plan's number to save it is precisely what removes the check.

### Phase 2b: Process detection (`procs.py`)

> Relocated from Part 2 because Phase 3's `cargo-target`/`dotnet-binobj` guards depend on it. Part 2 consumes it unchanged for browsers and editors. It sits **before** Phase 3 and not after: Phase 3 calls `procs.is_running()` in its tasks and patches it in its criteria, so a phase creating it later would leave Phase 3 unvalidatable — the same placement rule that moved a criterion at iteration 18. It is numbered `2b` rather than renumbered into the sequence because `Phase 3 task 5` and `Phase 4 task 3/4` are cited as authorities across all three plans, and shifting those labels would invalidate every cross-reference to buy nothing.

#### Tasks

1. `is_running(names)`: `tasklist /FO CSV /NH` via `subprocess`, parse image names case-insensitively, return the matched set — an **empty set** when the query succeeded and matched nothing.

    A missing or failing `tasklist` returns **`None`**, not an empty set. The distinction is the whole point and an empty set cannot carry it: both are falsy, so "unknown" would silently read as "not running" and a `warn-and-skip` module would delete a `target/` while a `cargo build` writes into it — the exact failure that guard exists to prevent, on the machines least able to report their process list. `None` is the package's established encoding of *unknown* (it already means unmeasurable for every byte count), so callers test `is None` before truthiness rather than reaching for a second flag.

A `warn-only` module is unaffected — it never skips anything — and a module declaring `proc_guard = None` never calls this function at all.
2. Never kill, never suspend, never elevate. Detection is informational.

3. When no `--root` is given the single default root is the **repo root** (master decision 15), and it is computed the way the import bootstrap already computes it - `Path(__file__).resolve().parent.parent.parent` - **never `Path.cwd()`**. This task is the authority on that derivation, because decision 15 names the root and no task derived it: `cwd` is the obvious guess and it is the dangerous one, since it equals the repo root only when the tool happens to be launched from there. A launcher-spawned action runs with its working directory set to **the script's own directory** - `resolve_action()` in `src/windows/process.rs` computes it as `script_path.parent()` and `build_action_command()` applies it through `current_dir` (verified, not assumed) - so under the launcher `Path.cwd()` is `scripts/winclean/` itself. `cwd` then fails in **two different ways depending on how the tool was started**, which is why the rule is "never `cwd`" and not "validate `cwd`". Under the launcher the default root would be winclean's own source tree: not a random directory but a specific plausible-looking one holding nothing to clean, so the run reports an almost empty plan and the user reads it as "this machine is clean" - a wrong answer that looks like a good one (decision 16). From a terminal it is wherever the shell happens to sit, which is an arbitrary tree walked at depth 6 - the same blast-radius error decision 15 was narrowed to prevent, arrived at from the other side. Silence in one mode, over-reach in the other; a guess that is only ever correct when the tool is launched from the repo root has no reading under which it is safe.

Discovery mode is a **three-valued** property: `walking` (searches under the roots), `fixed` (resolves a documented per-user path), `pathless` (reclaims through an external command and has no path at all — Part 2's `docker-light`). This task branches on the declared value and nothing else — it holds no list of module names, so adding a module cannot require an edit in two places. `fixed` and `pathless` modules are discovered **regardless of `--root`**. The plan says so explicitly, splitting its rows into "under your roots" and "per-user, outside your roots", because the opposite reading — that `--root D:\proj` confines the run to `D:\proj` — is a blast-radius misconception, not a cosmetic one. 4. Apply path: only with `--apply`. The primary guard of master decision 19 runs first: for a module declaring `proc_guard = warn-and-skip`, a `procs.is_running` result that is a non-empty set **or** `None` skips the candidate as **`skipped-running`** unless `--yes` was passed. **That token is defined here, and its absence was a gap rather than an implicit reuse of another status.** Every other skip path in this package has a name - `skipped-gone`, `skipped-changed`, `skipped-unconfirmed` - and Part 3 keys both the report and the JSONL history line on those names, so a skip with no name has exactly two implementations and both misreport: reuse `skipped-changed`, and the run tells the user the tree changed under it when in fact a build is running, which sends them to re-run and hit the same skip forever with the same wrong explanation; or omit the candidate from the report, and the plan promised bytes the summary silently does not account for, which reads as a lock or a bug. The reason string distinguishes *running* from *unknown* even though the status is shared, as the `None` criterion below already requires. Like every other skip it is **not an error** and does not affect the exit code (task 4's non-zero list is unchanged). Then, and only for candidates that have a path: re-`stat` the candidate and skip it if it is gone (`skipped-gone`) or its mtime moved since the plan (`skipped-changed`). **The plan-time value is stamped by the module's `discover()`, and this task is the authority on that**: the guard compares a value recorded before the plan was printed against one read now, so a `stat_mtime` filled at apply time would be compared with itself and the guard would never fire - inert, silently, in the step whose job is to notice a tree changing under the run. **A candidate whose plan-time `stat_mtime` is `None` is not skipped**: the guard does not run for it, which is the honest outcome for the directory trees where a mtime says nothing anyway (master decision 19 demotes this guard to secondary for exactly that reason, with `procs.is_running` as the primary). Treating `None` as *changed* is the other reachable reading and it skips every candidate no module chose to stamp, turning the tool into one that reports a full plan and removes nothing - a **secondary** guard whose directory-mtime limit is stated in master decision 19; then delete (or recycle per frozen decision 4 — at `safe`, the only level in this part, deletion is always **direct**). A **pathless** candidate (`path=None`, Phase 1 task 2b) takes neither branch: it has nothing to `stat` and nothing for `remove.py` to remove, so it goes straight to the module's own `clean()`. Both exclusions belong to this task rather than to whichever part first registers such a module — Part 2's `docker-light` would otherwise hit `os.stat(None)` here before ever reaching the routing rule. Accumulate `CleanResult` into a live structure. **A skip is never an error**: `skipped-gone`, `skipped-changed`, and the `no-undo` and `skipped-unconfirmed` outcomes the later parts add, are all reported and none of them affects the exit code. Non-zero is reserved for these causes and no others: a guard abort - which means an **abort**, and the dropped section of task 4 forces the distinction: a candidate refused as `protected` is reported and the run continues at `0`, because a user's own `PROTECTED_PATHS` (Part 3) is a legitimate cause and a run that failed every time a config protected something would be unusable; a candidate refused as `sanity` **aborts the run non-zero before any deletion**, naming the module and the path, because a drive root, the profile root or a path under 10 characters arriving from `discover()` means the component that computes deletion targets is defective, and finishing a plan built by it would be acting on the strength of the thing just proven wrong. Both are still listed in the dropped section; only one of them is an error, an over-ceiling plan, a validation error (unknown `--only` name, `--only` above the level, or — once Part 3 adds the config — a bad config key or an `--only` naming a config-disabled module: both are config-dependent, so neither is reachable in this part), a removal failure other than a lock, a **refused or unobtainable level confirmation** (Part 2 Phase 3 task 1), and an **interrupted run** — a `KeyboardInterrupt` or an unhandled exception raised after the first byte was removed. The list is stated once here and the later parts refer to it rather than re-deciding it per outcome; they refer to it by name, never by counting its entries, because a count is what drifts when a cause is added. It enumerates the non-zero exits the tool **chooses**: a traceback escaping discovery, before anything was removed, exits non-zero on Python's terms and is a defect to fix, not an entry to preserve — "and no others" governs designed outcomes, or the first crash in a `discover_*()` would read as a specification violation to be papered over with a `try`.
   The last two causes are the ones that look like exceptions to "a skip is never an error", and neither is. The **interrupted** run is not a skip at all: bytes are already gone and the run did not reach its end, so a caller reading `0` would record a completed cleanup that never happened — which is also why the interrupt is **caught** and turned into a controlled non-zero exit rather than left to escape as a traceback (the report still comes from the `finally` block, master decision 17, and Part 3 stamps that run `status: "interrupted"`). The **refused level confirmation** is not a skip either, because the two refusals are not the same event: refusing the **level** gate aborts the whole run before anything is touched — nothing was cleaned, so reporting success would be a lie to any caller — while refusing a **per-module** second confirmation (`package-cache`, Part 3) skips that one module and lets the rest of the run succeed, which is a `skipped-unconfirmed` outcome like any other. Whoever adds a future confirmation must place it on one side of that line, and say which. Print the estimated-vs-freed report **from a `finally` block** (master decision 17) so a `KeyboardInterrupt` after partial deletion still reports what is already gone, plus free space after.
5. `--out <path>`: write the report to `<path>` **in the same format stdout receives** — JSON when `--json` is also passed, the human-readable text otherwise. There is no third format and no format flag on `--out` itself.
