# Master Plan: winclean (Windows dev-machine disk cleaner, dry-run-first)

## Overview

- **Goal**: Build `scripts/winclean/`, a Python tool that **proposes** disk reclamation candidates and, only under an explicit `--apply`, removes them — reusing `scripts/system_inventory/` as its discovery layer and porting the safety model of the author's Linux tool [`sysclean`](https://github.com/RebelliousSmile/sysclean) onto Windows filesystem semantics. Three cleanup levels (`safe` / `moderate` / `aggressive`) ship across the three parts.
- **Risk Score**: 7/10
  - First tool in this repo that **deletes user data** (+4)
  - New package with 6+ cooperating modules, `ctypes` shell interop for the Recycle Bin (+2)
  - No breaking API change, no schema migration, `system_inventory` consumed read-only and left untouched (0)
  - Blast radius is genuinely high and irreversible where the Recycle Bin cannot be used: this is why dry-run is the default and why a byte ceiling aborts oversized plans.
- **Branch**: `feature/winclean/`

## Frozen decisions (from validated brainstorm — do NOT revisit)

1. **Separate package.** `scripts/winclean/` is new. `scripts/system_inventory/` stays **strictly read-only** — its documented "no `--apply`/`--fix` mode" contract is not broken; winclean *imports* it. `scripts/deps_audit/` is untouched.
2. **Dry-run is the default.** No deletion happens without `--apply` on the command line. There is no config key that can flip this — `--apply` is CLI-only, by design.
3. **Three levels from v1**, matching sysclean: `safe` (nothing irrecoverable is lost — but see decision 11: some `safe` items need the network to come back), `moderate` (heavy re-downloads, web sessions lost), `aggressive` (Recycle Bin contents, MSI Package Cache — requires interactive confirmation).
4. **Only `moderate` recycles by default. `safe` and `aggressive` delete directly.** Recycling an 8 GB `target/` is pointless: it fills the Recycle Bin and frees **zero** bytes, and undo has no value for something a build regenerates — hence `safe` deletes. Recycling the Recycle Bin is nonsense, and the MSI Package Cache is guarded by a double confirmation instead — hence `aggressive` deletes. Undo *does* have value for browser profiles and temp trees — hence `moderate` recycles. `--no-recycle` forces direct deletion; `--recycle` forces the Bin where possible. **The Bin-quota warning fires whenever a candidate is routed to the Bin — including the default `moderate` path, which is where it matters most, not only under an explicit `--recycle`.** It triggers when a single recycled candidate exceeds 10 % of its volume - and **10 % is a proxy, not the quota**: the real per-volume allowance is shell configuration the stdlib cannot read, so the tool compares against a figure it chose, not against the threshold Windows will apply. Past that real allowance the shell deletes permanently and silently, and the undo the level was chosen for would not exist. Two consequences follow and both are normative. The warning is worded as *may* exceed the Bin's allowance, never as a measurement - a proxy stated as fact becomes a false denial the day Windows changes its default. And **the absence of the warning is not a guarantee of undo**: a candidate under 10 % can still exceed a Bin configured smaller, so no message, footer or README line may present a recycled candidate as recoverable. Part 2 Phase 3 task 3b is the authority on the wording. This decision stated the opposite framing until iteration 71 and, being the document read first, was the one that mattered - and task 3b turned out to state both framings at once, its imperative unhedged and the correction appended below it, fixed in iteration 72. Part 2 owns the implementation.
5. **Recycling is not freeing.** The report distinguishes `freed` from `recycled`; a recycled total is never added to `freed`. This is a real divergence from sysclean, whose Linux trash module has no equivalent ambiguity.
6. **v1 is strictly non-elevated.** Windows has no non-interactive `sudo -n` probe (UAC is a GUI prompt), so sysclean's `root_ready()` pattern has no equivalent. Items that would require admin (`%WINDIR%\Temp`, WinSxS, Windows Update cache) are **reported as out-of-reach**, never attempted, never elevated.
7. **Never reimplement OS-owned cleanup.** WinSxS is only cleanable via `DISM /StartComponentCleanup`; shadow copies, `hiberfil.sys`, `pagefile.sys` are out of scope. Docker **volumes are never touched** (sysclean's rule, kept verbatim).
8. **`.vhdx` files are inventory-only.** Deleting does not reclaim; only `Optimize-VHD`/`diskpart compact` does. winclean reports them and refuses to include them in any plan.
9. **Stdlib only** (`argparse`, `json`, `os`, `sys`, `shutil`, `subprocess`, `dataclasses`, `pathlib`, `ctypes`), mirroring `system_inventory`. Tests via `python -m unittest`.
10. **Declarative module registry**, not sysclean's 20-branch `run_module()` dispatch and global `MODULE_EST`/`MODULE_MEAS` arrays: each module is a `CleanModule` record with `discover`/`clean` callables returning a `CleanResult`. One file + one test file per module family, as `system_inventory` already does.

### Decisions added by the shadow-areas pass of 2026-08-04

These close the gaps in `./2026_08_04-winclean-master-shadow-report.md`. They are frozen on the same footing as 1-10.

11. **`safe` means "nothing irrecoverable", not "rebuildable offline".** Every package-manager cache only refills with network access. `needs_network: bool` is **declared on the `CleanModule`**, stamped onto every candidate that module yields, marked in the plan, and excluded by `--offline`. It is not decided inside `discover_*()`: a value the registry declares and the discovery function overrides would drift silently past the mapping test. Purging those caches on a disconnected machine breaks every build until connectivity returns, and the level name must not hide that. See the single declaration site below.
12. **`--only` never escalates the level.** Naming a module above the active `--level` is an error that prints the required `--level` value and exits non-zero. Any other rule would make the `moderate`/`aggressive` confirmation bypassable from the command line. (`--only pycache` and `--only cargo-target` with no `--level` stay valid: both are `safe`, which is the default.)
13. **The parent's path-ownership rule is carried over.** `guards.absorb_nested()` drops any candidate that is a **descendant** of another and reports it as absorbed: the **ancestor wins**, because its own estimated size already includes the descendant's bytes and deleting it removes them anyway. Depth alone decides nesting; the ownership rank — a module's index in `registry_mod.py`'s single `MODULE_ORDER` tuple, derived rather than hand-declared so uniqueness is structural — only breaks a tie between two candidates on the **exact same** path. This kills both the double-counted estimate and the "parent deleted, child now fails on a vanished path" error class — the same problem `system_inventory` solved with `exclude_paths`. Absorption applies to the **discovered** set, not to a theoretical full set: under `--only pycache`, a `__pycache__` inside a `target/` has no ancestor candidate to be absorbed by and is therefore deleted on its own. That is intended.
14. **A failed `recycle()` never falls back to direct deletion.** The candidate is abandoned and counted in `failed` with reason `recycle-failed` - **with the candidate's measured size, never `0`**; Part 1 Phase 2 task 5 is the authority on where that figure comes from, and `0` would print this failure as an idle run. Only an explicit `--no-recycle` authorises direct deletion at a recycling level. A silent fallback would destroy the exact guarantee the level was chosen for.
15. **Frozen numeric defaults** (previously written as "e.g." or "depth-capped", which two implementers would have resolved differently):
    - `--max-delete-bytes`: **50 GiB**. High enough not to fire on a legitimate multi-`target/` dev machine, low enough to catch a path bug aimed at a profile root (hundreds of GiB).
    - `--max-depth`: **6** levels below each `--root`.
    - `TRASH_DAYS`: **7** days.
    - **Default `--root`: the repo root only.** `%USERPROFILE%\Documents` is *not* a default root — on this machine it is a MEGA-synced personal vault (`Documents\Perso\CLAUDE.md`), so every deletion there propagates to the cloud, and walking tens of GB of PDFs and media at depth 6 would blow the time budget for nothing. Cleaning other project trees is an explicit, per-invocation `--root` decision. When a resolved root sits under a known sync root (`Documents\Perso`, OneDrive, Dropbox, iCloud), the plan prints a **sync warning** naming it: deletions there are replicated remotely and the Recycle Bin does not undo the remote side.
    - **`--root` bounds the walking modules only.** The property is **three-valued**, not a boolean, and the third value is the one a binary reading loses: a module either walks the roots (`walking`), or resolves a documented per-user path (`fixed`), or has no path at all and reclaims through an external command (`pathless`). Only the first is bounded by `--root`; the other two are discovered whatever the roots hold, and the plan separates "under your roots" from "per-user, outside your roots" so `--root D:\proj` is never misread as confining the run to `D:\proj`. Restricting *which modules* run is `--only`/`--skip`, not `--root`. As with decision 11, this master does **not** enumerate which module is which — see the single declaration site below, which is also where the three values are named normatively.
    - Discovery of a `safe` plan over the default root: **≤ 60 s** on the target machine. Exceeding it means the depth cap is wrong, not that the criterion is. A user-supplied `--root` is not bound by this figure — it is a property of the default, not a promise about arbitrary trees.
16. **stdout is not a reliable output channel.** `build_command()` in `src/windows/process.rs` spawns every action with `CREATE_NO_WINDOW`, so a plan printed by a WinFXStart-launched `@python scripts/winclean/clean.py` is written to a console nobody sees. The terminal is therefore the **official** invocation path, and `--out <path>` writes the plan or report to a file for any non-terminal caller. Wiring winclean into `config/builtin-actions.json` is a separate product decision (Part 3, optional) — note that `bundled_python_actions_reference_existing_scripts` in `src/windows/process.rs` asserts an **exact count** of `@python` actions, so adding any would require updating that assertion. The number is deliberately not written here: the test is its own authority, this plan is not a mirror of it, and a figure copied into prose is wrong the day someone adds an unrelated action — the same reason the risk register below repeats no count from `guards.py`. Neither is the function pinned by line number, for the same reason. **Second verified fact about launcher-spawned actions, with two consequences the parts own:** `resolve_action()` sets the child's working directory to the script's own parent (`script_path.parent()`, applied by `build_action_command()` via `current_dir`), so under the launcher the working directory is `scripts/winclean/`. Hence the default `--root` is derived from `__file__` and never from `Path.cwd()` (Part 1 Phase 4 task 3, the authority), and any `--out` in a launcher action is absolute (Part 3 Phase 4 task 5). Both are the same fact read twice; neither part restates the mechanism as its own discovery.
17. **An interrupted `--apply` must still report.** Results accumulate in a live structure and the report is printed from a `finally`, so `KeyboardInterrupt` after partial deletion yields a partial report (Part 1) and a history line with `status: "interrupted"` (Part 3). A destructive run that leaves no trace defeats the purpose of having a history at all.
18. **Recycling defers reclamation; the tool says so and names a step that actually works.** Because `moderate` recycles by default (decision 4) and recycling does not free bytes (decision 5), a `moderate --apply` on its own can free **zero** bytes. That is intended, not a defect — the undo window is the point. What was missing is the actor closing the loop: winclean never empties the Bin implicitly. When a run recycled anything, the footer states the recycled total, that those bytes are **still on disk**, and three options, in this order:
    - `--no-recycle` on the next run, to skip the Bin entirely and reclaim immediately;
    - the Windows Recycle Bin UI, for an immediate emptying with visual confirmation;
    - `clean.py --level aggressive --only recycle-bin --apply --trash-days 0`, the scriptable equivalent.

    The `--trash-days 0` is **not** optional in that command: the default 7-day floor exists to protect a file deleted five minutes ago, so `recycle-bin` at its default is a *maintenance* module and by construction ignores exactly the bytes a `moderate` run just recycled. Printing the command without `--trash-days 0` would be printing a no-op, which is worse than printing nothing.
19. **The TOCTOU guard is the process check; the mtime check is secondary and its limit is stated.** A directory's `st_mtime` changes only when its **direct** entries change: a `cargo build` writing into `target\debug\deps\` leaves `target\`'s mtime untouched. So re-`stat`ing a candidate before removal catches a *replaced or top-level-modified* directory and nothing more — it must not be presented as closing the TOCTOU window. The primary guard is `procs.is_running`, and the honest residual risk is written in the README: winclean does not lock the tree it deletes, so deleting a build directory while a build runs corrupts that build. Nothing short of holding handles on every entry would fix it, which is out of scope for v1.

    **The guard has two strengths, and which module gets which is a declared property, not a global rule.** A running `cargo.exe` writing into `target\` means the tree is being *rewritten*, so deleting it corrupts a build that is under way: those modules are `warn-and-skip` — the candidate is warned about at plan time and **skipped** under `--apply` unless `--yes` acknowledges the warning. A running `chrome.exe` holding its cache open means the entries are *locked*, which is already a first-class reported outcome (`winerror 32` in `locked_paths`) and corrupts nothing: those modules are `warn-only` — they proceed and report what could not be removed. Written as one global skip rule, the ordinary `--level moderate --apply` with a browser open would silently skip every browser candidate, which is the opposite of what Part 2 asserts. The per-module strength is declared in `registry_mod.py` and asserted by a test, exactly as the discovery mode is. **An interactive confirmation answer covers the level gate only** — it is not an acknowledgement of a process warning, so a `warn-and-skip` candidate still needs `--yes` even on a TTY.

20. **Every user-facing string is French; every machine-readable token stays English.** Both sibling scripts already do this and nothing in `scripts/` does otherwise: `argparse` `description=`/`help=` in French (`system_inventory/inventory.py` lines 158-190, `deps_audit/audit.py` lines 212-221), printed reports and error lines in French (`"Aucun élément trouvé."`, `"Aucune source disponible : ..."`), and both `README.md` files in French - while docstrings, identifiers, `--json` keys and the sentinel `"unknown"` returned by `human_size` are English. winclean inherits the same split: the plan report, the estimated-vs-freed summary, every `help=`, every abort message and `scripts/winclean/README.md` are written in French; the `--json` payload keys, the run status values, the per-candidate reason codes and `"unknown"` stay English because a consumer parses them.

    **Consequence for these four plan files: an English string quoted in them specifies the *content* of a message, never a literal to copy.** "A message naming `--level moderate`" means the French message contains the token `--level moderate` - and the test asserts the token, not the sentence, so a reworded French message never breaks a test. This is stated once, here; the parts point at this decision rather than restating it, and Part 1 Phase 4 task 6 is where it lands in the README.

### The single declaration site for the three per-module properties

Decisions 11, 15 and 19 each constrain one column of the **same** table. That table lives in exactly one place: **Part 1 Phase 3 task 5, `registry_mod.py`** — `discovery` (`walking` | `fixed` | `pathless`), `proc_guard` (`warn-and-skip` | `warn-only` | `None`), `needs_network` (`bool`). All three are `CleanModule` fields with **no default**, so registering a module without classifying it is an import-time `TypeError` rather than a silent default, and `tests/test_registry_mod.py` asserts each column over the *currently registered* set so adding a module without a declaration fails the suite. Parts 2 and 3 extend the same table and the same tests.

This master states the rules and never enumerates which module is which — one authority, no drift. `ownership_rank` is deliberately **not** in that table: it is derived from the `MODULE_ORDER` tuple (decision 13), so its uniqueness is structural rather than asserted.

### Two orthogonal axes (do not conflate)

Decisions 2 and 4 govern **different** things. Whether anything is deleted is `--apply`. *How* it is deleted is the level's removal mode. Dry-run applies to every level, `safe` included.

| Level | Default (no `--apply`) | With `--apply` | Removal mode | Confirmation |
| ----- | ---------------------- | -------------- | ------------ | ------------ |
| `safe` | plan printed, **zero deletion** | deletes | **direct** — recycling regenerable artefacts frees nothing and undo has no value | none — regenerable only (but `--yes` is still meaningful here: it acknowledges a `warn-and-skip` process warning, its other effect) |
| `moderate` | plan printed, **zero deletion** | deletes | **Recycle Bin** when `can_recycle()`, else skipped as `no-undo` | interactive, or `--yes` |
| `aggressive` | plan printed, **zero deletion** | deletes | **direct** — recycling the Recycle Bin is nonsense | interactive, or `--yes` + a second one for `package-cache` (interactive answer or `--yes-package-cache`; `--yes` does **not** cover it) |

This table is the authority on removal mode; decision 4 states the same three modes in prose. `moderate` is the **only** recycling level.

`--apply` is CLI-only and never inferred: not from the level, not from the config file, not from `--yes`. Per decision 12, `--only` cannot raise the level either — it filters **within** the active level.

`--yes` has exactly two effects, and no others: it answers a confirmation that the level already requires (`moderate`, `aggressive`), and it acknowledges a **running owner-process warning** on a `warn-and-skip` module (decision 19), which is the only reason it is meaningful at `safe` — without it, a `cargo-target` candidate whose `cargo.exe` is running is skipped rather than deleted. It never raises the level, never implies `--apply`, and on its own deletes nothing. The two effects are independent: answering the interactive prompt grants the first only, so `--yes` remains the sole way to obtain the second even on a TTY.

Because that list is exhaustive, `--yes` does **not** answer `package-cache`'s second confirmation: that one takes an interactive answer or the module-specific `--yes-package-cache`, and with neither, `package-cache` alone is skipped while the rest of the plan runs (Part 3). Symmetrically, `--recycle` is accepted and **inert** at `safe` and `aggressive` — `moderate` is the only level whose removal mode it can influence, and forcing the Bin on `recycle-bin` would mean recycling the Recycle Bin.

- Every module returns `list[CleanCandidate]` from `discover()` (path **or** `None` for a command-based candidate, label, estimated bytes, level, reason) and a `CleanResult` from `clean()`. The fields are **not** enumerated here: Part 1 declares the initial set in `common.py`, Parts 2 and 3 each add one, and this section describes the *target* package — an enumeration frozen at Part 1's set would be contradicted by its own children the moment they land, which is how the `unmeasurable` boolean survived here after Part 1 dropped it. The one rule that holds across all three parts and belongs here: byte counts are nullable and `None` is the package's **single** encoding of *unmeasurable*, never a companion boolean. `path=None` exists from Part 1's first commit for `docker-light`'s sake: the guard chain skips pathless candidates instead of a module bypassing the guards to ship one. Every path-typed step excludes them, not only the guards — the ceiling still counts their estimate, but the TOCTOU re-`stat`, `remove.py` and `can_recycle()` are all skipped and such a candidate goes straight to its module's `clean()`. Stated once here because the exclusion is needed in three different phases across two parts, and each of them discovered it as a crash rather than as a rule.
- `clean.py` resolves config → builds the plan → prints it → stops, unless `--apply`.

## Why three parts (independence)

- **Part 1** establishes everything dangerous **once**: the candidate/result model, the guard layer (casefolded protected paths, `\\?\` long-path prefixing, path sanity thresholds, the `--max-delete-bytes` ceiling), the deletion primitive including the Recycle Bin interop, and the first module family — dev build artefacts, which are 100% regenerable and therefore the correct place to first exercise real deletion. After Part 1, `python scripts/winclean/clean.py` prints a plan and `--apply` reclaims `target/`, package-manager caches and `__pycache__`. No later part is required.
- **Part 2** adds the `moderate` family on top of the unchanged Part 1 primitives: browser and editor caches, `%TEMP%`, `CrashDumps`, `docker system prune` (never volumes). It also adds what Linux never needs — **locked-file handling**: a `WinError 32` mid-tree is a normal, reported partial outcome, not a crash. Strictly additive; `safe` behaviour is unchanged.
- **Part 3** adds the `aggressive` family (`$Recycle.Bin` per volume with `--trash-days`, MSI Package Cache with its uninstall/repair warning), plus the operational layer sysclean has and Part 1-2 defer: an allowlisted config file, JSONL run history with `--history N`, and the estimated-vs-measured comparison report. Additive again.

## Cross-cutting risk register

| Risk | Impact | Mitigation |
| ---- | ------ | ---------- |
| **Path bug deletes the wrong tree** | Irreversible data loss | Layered, all in Part 1 — Part 1's `guards.py` is the authority on the set, so no count is repeated here: protected-path match on the **resolved, casefolded** path incl. recursive subtree; refusal of paths shorter than 10 chars, of `%USERPROFILE%`, of any drive root; `--max-delete-bytes` ceiling aborting the whole plan before the first deletion; dry-run default |
| **Case-insensitive paths defeat protection** | A protected path written in another case protects nothing | Every comparison goes through `os.path.normcase` + resolution — sysclean's raw string compare in `path_protected()` is **not** portable here; unit-tested with mixed-case input |
| **`MAX_PATH` (260) breaks deletion mid-tree** | Half-deleted `node_modules`, unusable state | All deletion paths prefixed `\\?\` (absolute, **already resolved** - the prefix disables normalisation, so a `..` would survive it - backslash-normalised), and the prefixed form **never leaves `remove.py`**: it is a syscall spelling, not a stored value (Part 1 Phase 2 task 1 owns the containment rule); unit-tested against a deliberately >260-char nested tree |
| **Recycle Bin cannot take long paths** | Silent fallback to irreversible deletion | `SHFileOperationW` is MAX_PATH-bound and rejects `\\?\`; a candidate over the limit — or on a volume `kernel32.GetDriveTypeW` does not report as `DRIVE_FIXED`, which is the predicate `can_recycle()` actually uses — is marked `no-undo` and requires explicit `--no-recycle`, otherwise it is skipped and reported. Not "off the profile volume": every fixed volume owns its own `$Recycle.Bin`, and Part 3's `recycle-bin` module enumerates all of them, so a second internal disk recycles normally while a network share or a removable drive does not |
| **Recycle Bin quota overflow deletes permanently and silently** | User believes an item is recoverable when it is not | Report recycling as `recycled`, never as recoverable-guaranteed; per decision 4 the plan warns when a single Bin-routed candidate exceeds 10 % of its volume, on the default `moderate` path too (Part 2, unit-tested); quota caveat in the README |
| **`shutil.rmtree` follows a junction out of scope** | Deletion outside the intended tree | Reparse points are deleted **as entries**, never descended into (`os.path.islink` + `st_file_attributes & 0x400`); `rmtree` is only ever called on verified non-reparse directories |
| **Locked files (`WinError 32`)** | Crash mid-run, or a false "cleaned" claim | Per-entry `OSError` capture; partial success is a first-class reported state with a `failed` byte count; never retried in a loop, never force-unlocked |
| **Estimated bytes ≠ freed bytes** | Misleading report | `estimated` and `measured` are separate fields **and separate measurements** - Part 1 Phase 2 task 5 pins `measure_freed`'s input to a per-candidate pre-operation walk, because two fields fed by one number agree by construction and audit nothing; unmeasurable is `null`, never `0` (sysclean's `MEASURE_UNKNOWN` distinction, kept). The reused `dir_size_on_disk` cannot itself report unmeasurable — it swallows per-entry errors and returns an `int` — so Part 1 task 3b makes `null` reachable where it matters (an unreadable candidate **root**) and states plainly that a denied subtree *inside* a readable candidate makes the estimate silently low.
